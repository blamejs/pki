# Roadmap

`@blamejs/pki` is a pure-JavaScript (CommonJS) PKI toolkit: X.509, CMS, OCSP, timestamping, and the PKCS enrollment and certificate formats, built post-quantum-first with no npm runtime dependencies and security defaults wired in rather than opt-in. It reimplements the standards surface of the classical PKI.js toolkit while owning its own ASN.1 codec and crypto layer, so correctness, denial-of-service resistance, and algorithm agility are in-tree rather than inherited from external parsers or the Web Crypto ceiling.

This document tracks capability areas and the standards they target, in rough delivery order. Every item is marked **Shipped** (available in the current release), **Targeted** (committed for a near-term release), **Planned** (accepted, scheduled later), or **Under design** (shape still being settled). Status changes as capabilities ship; the changelog is the record of what is released today.

## Foundations

The parser and algorithm layers are the load-bearing decisions the rest of the library rides on.

- **Strict, validating DER/BER codec** — *Shipped.* An in-house ASN.1 encoder and decoder with a hard depth and size bound, so malformed or deeply nested input is rejected in bounded time instead of exhausting the stack. DER is canonical on encode. The decoder rejects non-canonical structures by default and accepts BER only where a specific standard permits it. A single structure definition drives both encode and decode, so context-tag (EXPLICIT/IMPLICIT) handling cannot diverge between the two directions.
- **Data-driven algorithm registry** — *Shipped.* The OID registry (`pki.oid`) names every algorithm, attribute, and extension in both directions, and the resolution table maps an OID to its parameters, key importer, signer, and verifier. A signature or KEM algorithm, including the post-quantum sets, is therefore a registry entry rather than a special case across signing, verification, and path validation.
- **Node-native crypto engine** — *Shipped.* Cryptographic operations run over Node's native `node:crypto` through the W3C WebCrypto engine (`pki.webcrypto`), which removes the Web Crypto limits on streaming, opaque (non-extractable) key handles, and algorithm coverage. It ships the full classical set plus post-quantum ML-DSA and SLH-DSA signatures and ML-KEM key generation, encoding, import, encapsulation, and decapsulation, the last two being what the CMS `KEMRecipientInfo` arm rides on.
- **Fail-closed operation** — *Shipped.* Every decode, encrypt, sign, and verify path throws on failure through the typed `PkiError` taxonomy. No path emits zero, default, or partial output in place of a real result.

## X.509 certificates and CRLs — RFC 5280

- **Certificate parse / build / sign / verify** — *Parsing and signing shipped.* `pki.schema.x509.parse` decodes a v3 certificate, and `pki.x509.sign(spec, issuer, opts)` builds and signs one, self-signed from a key alone or CA-signed from an explicit issuer name and public key or an issuing certificate, returning DER or a PEM `CERTIFICATE`. The signature algorithm is resolved from the signing key through the shared registry, so RSA (PKCS#1 v1.5 and PSS), ECDSA on P-256/P-384/P-521, Ed25519, Ed448, ML-DSA-44/65/87, the twelve SLH-DSA sets, and the composite (hybrid) arms are all available. It encodes the extension set from the spec — basic constraints, key usage and extended key usage, subject and authority key identifiers, subject alternative names, and certificate policies — with any other extension supplied as pre-encoded DER. It derives the version from the field set (v3 with extensions, else v1) and enforces the RFC 5280 serial-number bounds, the UTCTime/GeneralizedTime cutover, the DER default omissions (v1 tag, false criticality, false cA), and the CA cross-field rules (keyCertSign and path length require cA). Every emitted certificate round-trips through the parser and is independently verified by OpenSSL across every algorithm arm. The remaining standard extension encoders (name constraints, policy constraints and mappings, CRL distribution points, authority and subject information access) land natively as the demand appears; the pre-encoded-DER form covers them now. RFC 5280 / RFC 9909 (SLH-DSA) / RFC 9882 (ML-DSA).
- **Distinguished names as ordered RDN collections** — *Shipped.* Names are modeled as an ordered sequence of relative distinguished names, each an unordered set of type/value pairs, so multi-valued RDNs parse, encode, and compare under the RFC 5280 §7.1 canonical DN equality across every format.
- **CRLs** — *Shipped.* `pki.schema.crl.parse` decodes a certificate revocation list, and `pki.path.crlChecker` performs revoked-certificate lookup with signature, issuer-authorization, distribution-point-scope, and currency checks. `pki.crl.sign` builds and signs a `CertificateList` (RFC 5280 §5) over any registry algorithm: the version derived from the extension set, an empty revocation list omitting the field, `reasonCode` an ENUMERATED and `invalidityDate` always GeneralizedTime, and the CRL and entry extensions (authority key identifier, cRLNumber, issuing distribution point, delta-CRL indicator, freshest CRL, authority information access, reason code, invalidity date) with their RFC-fixed criticality. Two shapes are refused rather than emitted: `certificateIssuer`, and an issuing-distribution-point marked `indirectCRL`. `pki.path.crlChecker` skips an indirect CRL outright, so signing one would produce a list this toolkit's own checker would never treat as authoritative; both are re-enabled once the checker processes indirect CRLs. `pki.crl.verify` checks a CRL signature through the one path-validation signature engine, and `pki.crl.isRevoked` looks a serial up. Reason coverage accumulates across corresponding distribution points until all eight revocation reasons are covered (§6.3.3(d),(l)), so a CA that partitions revocations by reason code reaches a verdict. A delta CRL is merged onto a complete CRL it may be combined with (§5.2.4 / §6.3.3(c)) — the delta searched first, then the base, with `removeFromCRL` releasing a held certificate — gated on `useDeltas` and a `freshestCRL` locator; merging may only turn undetermined into good or revoked, never a revoked into a good. Cross-checked against OpenSSL.
- **Human-readable inspection (`openssl x509/crl/req/cms -text` in pure JS)** — *Shipped.* `pki.inspect.certificate`, `.crl`, `.csr`, and `.cms` turn a certificate, certificate revocation list, PKCS#10 request, or CMS message (PEM, DER, or a parsed result) into the familiar OpenSSL-style report, and `pki.inspect.any` detects the format and routes to the right one, so an operator reads a PEM or DER blob without shelling out to OpenSSL. A certificate report shows version, serial, signature algorithm, the issuer and subject distinguished names, the validity window, the public-key details, and every decoded extension. A CRL shows the issuer, Last and Next Update, the CRL extensions, and each revoked entry with its serial, revocation date, and named reason code. A CSR shows the subject, the public key, and the requested extensions and attributes. A CMS SignedData shows the content type, digest algorithms, embedded certificates, and each SignerInfo with its signer identifier, algorithms, signed and unsigned attributes, and signature, with a stable top-field summary for a non-SignedData ContentInfo. All four compose one set of field renderers over the strict parsers, the shared extension decoders, and the two-way OID registry, so they name the same vocabulary the verifier resolves, name OIDs an OpenSSL build shows only as raw octets, and cannot drift. An unregistered OID renders as its dotted string and an undecodable value as raw octets. The report is best-effort: a malformed part hex-dumps rather than sinking the report, and only entry-point coercion throws. The format is stable and OpenSSL-familiar rather than pinned to one OpenSSL version, and is verified field for field against `openssl x509/req/cms -text`. `pki.schema.detectFormat` is the detection companion of `pki.schema.parse`.
- **Qualified certificate statements** — *Shipped.* `pki.schema.x509.parse` decodes the RFC 3739 §3.2.6 / ETSI EN 319 412-5 `qcStatements` extension: the EU qualified-certificate declaration (QcCompliance), reliance limit (QcLimitValue), QSCD-key flag (QcSSCD), certificate-purpose type (QcType), retention period, PDS URLs, country of qualification, and the PKIX SemanticsInformation statements. They are decoded and validated by the toolkit's certificate-extension decoders and rendered by `pki.inspect`, with an unknown statement preserved opaque and every malformed shape failing closed as a typed error. RFC 3739 / ETSI EN 319 412-5.
- **Microsoft enterprise CA extensions** — *Shipped.* `pki.schema.x509.parse` decodes the Active Directory Certificate Services enrollment extensions and `pki.inspect` renders them: the v2 certificate template marker (`szOID-CERTIFICATE_TEMPLATE`, the template OID plus its major and minor version, each a full DWORD), the legacy v1 template name (`szOID-ENROLL_CERTTYPE_EXTENSION`, a BMPString), the CA version (`szOID-CERTSRV_CA_VERSION`, surfaced both as the raw DWORD and split into the CA key index and certificate index), the previous-CA-certificate hash (`szOID-CERTSRV_PREVIOUS_CERT_HASH`), and the application policies (`szOID-APPLICATION_CERT_POLICIES`, decoded with the same rules as RFC 5280 certificate policies). Each fails closed as a typed error on a malformed shape, and a critical instance is rejected in certification-path validation and flagged by `pki.lint`. [MS-WCCE] / [MS-CRTD].

## Certification requests — RFC 2986 (PKCS#10)

- **CSR parse / build / sign / verify** — *Shipped.* `pki.schema.csr.parse` decodes a PKCS#10 request, `pki.csr.verify(request)` checks an inbound one's proof of possession, and `pki.csr.sign(spec, key, opts)` builds and signs one, self-signed by the subject's own key for proof of possession with no issuer, over any signature algorithm the registry resolves (RSA PKCS#1 v1.5 and PSS, ECDSA, EdDSA, ML-DSA, SLH-DSA, composite). First-class helpers accept strings and plain objects: a subject, which may be empty, a `challengePassword`, and an `extensionRequest` carrying the requested v3 extensions (subject alternative names, key usage, extended key usage, basic constraints, certificate policies, subject key identifier, or pre-encoded Extension DER) that a CA copies into the issued certificate. The produced request's proof-of-possession signature is verified against the subject key before it is returned, which is what `openssl req -verify` checks, and every emitted request round-trips through the parser and OpenSSL. On the receiving side `pki.csr.verify` answers the same question about a request someone else produced, through the path-validation signature engine. RFC 2986 / RFC 2985.

## Certification path validation — RFC 5280

- **Path validation engine** — *Shipped.* `pki.path.validate` runs the RFC 5280 §6.1 validation algorithm over an ordered path and a trust anchor: signature chaining, validity windows, name chaining, key usage, basic constraints and path length, name constraints, and the certificate-policy tree. Trust anchors may be roots or intermediates.
- **Path building** — *Shipped.* `pki.path.build(leaf, opts)` discovers the ordered leaf-to-anchor path `pki.path.validate` consumes, from a leaf certificate, an untrusted pool of candidate CA certificates, and a trust store. Candidate issuers are matched by RFC 5280 §7.1 name chaining and prioritized by the RFC 4158 §3.5 heuristics — a subjectKeyIdentifier/authorityKeyIdentifier match, an anchor-adjacent issuer, CA plus keyCertSign, validity at the check time — all of which are ordering hints rather than filters. They are then searched depth-first with backtracking, so the first path `validate` accepts wins. A name or key-identifier match is only a hint, and every accept flows through `validate`, so building never weakens or duplicates a §6.1 check. A chain-length cap, a total-work cap on candidate expansions, and a visited set keyed on the certificate identity tuple bound the search over the untrusted pool, so a cross-certificate cycle or Bridge-CA fan-out terminates deterministically. The trust store accepts anchor tuples or self-signed root certificates, `opts.validate:false` returns the ordered path unvalidated, and the accept-or-reject verdict is cross-checked against `openssl verify`. Opt-in AIA `caIssuers` network fetching is shipped: `opts.fetchAia: true` discovers a missing intermediate from a certificate's Authority Information Access `caIssuers` URL (RFC 5280 §4.2.2.1) over `pki.transport`, explored as a lazy fallback only after the local candidate pool is exhausted (RFC 4158 §7.2, local before remote), so a build the pool can complete never touches the network. It is bounded against SSRF and amplification: HTTPS-only; no private, loopback, or link-local destination, whether such an IP literal or a hostname that resolves to one, with the checked address pinned for the connection; a total fetch budget enforced as a silent cap, stopping fetching rather than throwing and denying a buildable path; a per-cert URL cap; a build-wide URL dedupe; a response size and certificate-count cap; no redirect following; and every fetch fault a silent skip. Every fetched certificate is untrusted pool material that still flows through `validate`, never a trust anchor. It is off by default, so the default build is byte-identical offline. Reverse and bridge-mesh building and multiple-anchor policy selection remain *Planned*. RFC 4158 / RFC 5280 §4.2.2.1 / §6.
- **Structured results** — *Shipped.* Validation returns the complete path plus a per-check reason code for every step. Validity-window enforcement is always on, with the check date an explicit input. Validation is pure and re-entrant: input certificate state is never mutated, so a chain can be validated repeatedly.
- **Revocation checking** — *Shipped (CRL and OCSP).* A pluggable revocation hook is integrated into the path result. `pki.path.crlChecker` consults CRLs, checking signature, issuer authorization, distribution-point scope, and currency. `pki.path.ocspChecker` consults pre-fetched OCSP responses (RFC 6960) over the same interface: matching the full CertID triple against the certificate, recomputing `issuerNameHash` and `issuerKeyHash` under the CertID's own hash algorithm, confirming the responder is authorized (the issuing CA directly, or a CA-issued delegate bearing id-kp-OCSPSigning), verifying the response signature, and enforcing `thisUpdate` and `nextUpdate` currency. Both fail closed to an undetermined status unless the caller opts into soft-fail. RFC 6960.
- **Adversarial conformance corpus** — *Targeted.* Name-constraint and path-validation behavior is gated against a public adversarial corpus.

## Cryptographic Message Syntax — RFC 5652

- **SignedData** — *Signing and verification shipped.* `pki.cms.sign(content, signers, opts)` produces a CMS SignedData (RFC 5652 §5) and `pki.cms.verify(input, opts)` verifies one, both over attached and detached content, single- and multiple-signer, across RSA, RSASSA-PSS, ECDSA, EdDSA, and the post-quantum ML-DSA-44/65/87 (RFC 9882). Signing builds the signed attributes (content-type, message-digest, signing-time, plus any caller-supplied attribute) as canonical DER, signs the exact §5.4 preimage, and emits a DER `Buffer` or PEM; the signer identifier is issuerAndSerialNumber or subjectKeyIdentifier. Verification locates each signer certificate by its issuerAndSerialNumber or subjectKeyIdentifier, embedded or caller-supplied, and checks the signature over the exact §5.4 preimage: with signed attributes present, the message-digest attribute must equal the content digest and the signature covers the DER re-encoding of the SignedAttributes, with the on-wire `[0]` implicit tag replaced by a universal SET OF; otherwise the signature covers the content directly. Each parameter comes from the correct structure, keeping the content digest, the signer's digest algorithm, and the key's own algorithm identifier distinct, and verification reports a per-signer verdict, deferring the trust chain to the caller's `pki.path.validate`. Countersignatures and unsigned attributes are shipped: `pki.cms.countersign` adds an RFC 5652 §11.4 countersignature (a `SignerInfo` over the countersigned signature value, any signer algorithm, nestable, with the primary bytes preserved), and `pki.cms.verify` returns each countersignature's verdict under `signers[i].countersignatures` and every unsigned attribute — including an RFC 3161 timestamp token, attachable via `pki.cms.sign`'s `unsignedAttributes` — under `signers[i].unsignedAttrs`, surfaced unauthenticated. Composite-signature `SignerInfo` signing and verification are shipped; see **Composite (hybrid) signatures**. Certs-only certificate-management messages are shipped: `pki.cms.certsOnly` builds a degenerate SignedData that conveys certificates and CRLs without signing anything (RFC 8551 §3.8), `pki.cms.parseCertsOnly` reads one back to its raw certificate and CRL DER (accepting a CRL-only message, unlike the cert-required RFC 5272 form that `pki.est.parseCertsOnly` reads), `pki.cms.isCertsOnly` recognizes one structurally, and `pki.smime.buildCertsOnly` wraps it in the `application/pkcs7-mime; smime-type=certs-only` S/MIME entity, read back by OpenSSL's `pkcs7 -print_certs`.
- **EnvelopedData with a first-class recipient model** — *Shipped.* `pki.cms.encrypt` and `pki.cms.decrypt` encrypt and decrypt with all five RFC 5652 recipient types: key transport (RSAES-OAEP-SHA256/384/512, with PKCS#1 v1.5 decrypt-only under the RFC 3218 implicit-rejection countermeasure and never emitted), key agreement (ephemeral-static ECDH over P-256/384/521 with the ANSI-X9.63 KDF, and X25519/X448 with HKDF per RFC 8418), symmetric key wrap (AES-128/192/256 key wrap), password (PBKDF2 with the RFC 3211 PWRI-KEK), and the post-quantum ML-KEM KEMRecipientInfo. Recipient identification is pluggable: issuer-and-serial and subject-key-identifier for both directions. One fresh content-encryption key is wrapped for every recipient, and content is AES-128/192/256-GCM (an authenticated AuthEnvelopedData) or -CBC. Key agreement follows RFC 5753 / RFC 8418. Both directions cross-check against `openssl cms`.
- **EncryptedData** — *Shipped.* `pki.cms.encrypt` and `pki.cms.decrypt` protect content with a raw predefined key (`{ cek }`) or a PBES2 password (`{ password }`, RFC 8018). RFC 5652 §8.
- **AuthenticatedData** — *Shipped.* `pki.cms.authenticate` produces an `id-ct-authData` (RFC 5652 §9): cleartext content plus an HMAC-SHA-256/384/512 MAC, with the fresh MAC key wrapped for every recipient through the same RecipientInfo model EnvelopedData uses (RSA, EC, X25519, X448, ML-KEM, password, key wrap). By default the MAC covers the authenticated attributes (content-type and message-digest of the content) re-tagged to the EXPLICIT SET OF (§9.2); with authenticated attributes off it covers the content octets directly. `pki.cms.decrypt` recovers the MAC key, recomputes the MAC over the exact §9.2 preimage, and independently recomputes the message-digest (§9.3, do-not-trust-originator) before releasing the content, with every secret-dependent failure — wrong key, forged MAC, digest mismatch — collapsing to the one uniform `cms/decrypt-failed` so a MAC failure leaks no unwrap-success bit. Cross-checked against an independent OpenSSL HMAC over the reconstructed preimage. RFC 5652 §9, RFC 2104, RFC 4231.
- **AuthEnvelopedData** — *Shipped.* `pki.cms.encrypt` produces and `pki.cms.decrypt` verifies an `id-ct-authEnvelopedData` with AES-128/192/256-GCM content, the authenticated default. The authenticated attributes are MACed under their EXPLICIT SET OF re-encoding (RFC 5083 §2.2), and GCMParameters carry the nonce and a 16-octet ICV matching the mac length (RFC 5084). Integrity is verified before any plaintext is released. RFC 5083 / RFC 5084.
- **KEMRecipientInfo** — *Shipped.* `pki.cms.encrypt` and `pki.cms.decrypt` produce and consume the `id-ori-kem` OtherRecipientInfo arm end to end: ML-KEM-512/768/1024 encapsulation, the `CMSORIforKEMOtherInfo` KDF-info rebuilt identically on both sides, and HKDF-SHA256 to the wrap key (512 to aes128-wrap, 768 and 1024 to aes256-wrap), with version 0, kekLength-to-wrap consistency, and FIPS 203 ciphertext sizes enforced before decapsulation. RFC 9629 / RFC 9936.
- **CompressedData** — *Shipped.* `pki.cms.compress` and `pki.cms.decompress` produce and consume an `id-ct-compressedData` (RFC 3274): ZLIB (RFC 1950 / RFC 1951) compression, version 0, `id-alg-zlibCompress` with omitted parameters, and the RFC 1950 stream as the encapsulated content. Decompress bounds the uncompressed output at `C.LIMITS.COMPRESS_MAX_BYTES` (16 MiB, tightened downward via `opts.maxOutputBytes`) and stops before the output is materialized, so a decompression bomb fails closed as `cms/decompress-too-large` rather than exhausting memory. CompressedData is a size transform only, with no integrity, confidentiality, or authentication (RFC 8551 §2.4.5). RFC 3274.
- **Streaming CMS** — *Shipped.* A detached signature can be produced and verified over a streamed content, an async iterable of byte chunks, so a large payload is signed and checked without being held in memory. `pki.cms.sign` and `pki.cms.verify` take the streamed content; the payload is hashed incrementally under every signer's digest algorithm in one pass. `pki.cms.encrypt` also takes a streamed plaintext, running it through the AES-GCM or AES-CBC content cipher incrementally so a large payload is encrypted without being buffered whole; the ciphertext is assembled before the definite-length encryptedContent DER is emitted, and the output is byte-for-byte the buffered form. `pki.cms.decrypt` takes `opts.stream: true`, which returns the recovered `content` as an async iterable of plaintext chunks: an AuthEnvelopedData, an AuthenticatedData, and the AEAD path verify integrity before the iterable yields, so a forged message throws `cms/decrypt-failed` before any plaintext is exposed, while a CBC EnvelopedData or EncryptedData yields the plaintext as the cipher produces it and a corrupt message still collapses to the same uniform `cms/decrypt-failed`.

## Keys and credential stores

- **PKCS#8 private keys and SPKI public keys** — *Shipped.* `pki.key.export` and `pki.key.import` move a private key as PKCS#8 or a public key as SubjectPublicKeyInfo, with the algorithm parameters delegated to the encoder so RSA carries an explicit NULL, EC a named curve, and Ed25519/Ed448/X25519/X448 omit parameters. `pki.key.generate` and `pki.key.publicFromPrivate` produce and derive keys over RSA, EC, the Edwards and Montgomery curves, and the post-quantum ML-DSA and ML-KEM. RFC 5958 / RFC 5280.
- **Password-based encryption** — *Shipped.* `pki.key.encrypt` and `pki.key.decrypt` protect a private key as an RFC 5958 EncryptedPrivateKeyInfo under RFC 8018 PBES2 (PBKDF2 with AES-CBC), with UTF-8 password encoding, correct for non-ASCII passwords; byte-exact-with-OpenSSL parameters, omitting a default pseudorandom function and keyLength; salt and iteration counts bounded against a denial-of-service cap before any derivation; and a fail-closed decrypt that is not a padding oracle. PBES1, PBMAC1, and scrypt are refused. RFC 8018.
- **PKCS#12 (PFX)** — *Shipped (parse, build, MAC, read; both integrity and both privacy modes).* Parse key-and-certificate stores: authenticated safe, cert / CRL / key / secret bags, shrouded key bags with the algorithm surfaced and the ciphertext opaque, nested safe contents, `friendlyName` and `localKeyId` attributes, and MAC integrity surfaced with the exact MACed byte range, with RFC 9579 PBMAC1 recognized. BER content regions (indefinite lengths, constructed octet strings) are accepted exactly where §4.1 requires them, and interoperability with OpenSSL is a release acceptance gate. `pki.pkcs12.build`, `pki.pkcs12.verifyMac`, and `pki.pkcs12.open` assemble, MAC-verify, and read back a password-integrity store: every bag type, shrouded keys and cert safes encrypted under PBES2, a classic Appendix B HMAC or an RFC 9579 PBMAC1 MAC, with the PKCS#12 BMPString/UTF-8 password split that makes a file open in OpenSSL and NSS, cross-checked bidirectionally. `open` verifies integrity before decrypting, so a wrong password is the MAC verdict; returns the keys as re-validated PKCS#8 DER and the certs, CRLs, and secrets as raw DER; and refuses a MAC-less store, unless opted in, or a legacy non-PBES2 bag. Public-key (signedData) integrity is shipped: `build` with `opts.integrity.mode: "public-key"` wraps the AuthenticatedSafe in a CMS SignedData — a signature from any `pki.cms.sign` signer algorithm (RSA, ECDSA, EdDSA, ML-DSA, SLH-DSA, composite) with no MacData, RFC 7292 §4 — and `open` verifies that signature as the integrity gate before any bag is trusted, surfacing the per-signer verdict in `signers` without trust-chaining it, which remains the caller's `pki.path.validate` step. Public-key privacy is shipped: `build` with per-safe `recipients`, or the `opts.recipientCerts` convenience, wraps a SafeContents as a CMS `EnvelopedData` (AES-CBC, `id-envelopedData`, never GCM) encrypting it to recipient public keys through the shipped `pki.cms.encrypt` recipient model, restricted to certificate recipients (RSA-OAEP, ECDH, X25519, X448, ML-KEM) since a password or KEK recipient could not be reopened by `open`; and `open` with `opts.recipientKey` decrypts it via `pki.cms.decrypt` after the integrity gate, every recipient-side fault collapsing to a uniform `pkcs12/decrypt-failed`. Privacy is independent of integrity, so all four integrity-by-privacy combinations are permitted (RFC 7292 §3.1). Legacy-PBE read is shipped: `open` decrypts the RFC 7292 Appendix C schemes an `openssl pkcs12 -legacy` or NSS store uses — 3-key and 2-key Triple-DES-CBC and 40- and 128-bit RC2-CBC bags, via the Appendix B KDF over the BMPString password, with RC2 through an in-tree RFC 2268 cipher since OpenSSL 3.x moved RC2 to its legacy provider — with the iteration count DoS-capped and every secret-dependent failure the uniform `pkcs12/decrypt-failed`. The legacy RC4 schemes are named and refused. RFC 7292, RFC 9579, RFC 8018, RFC 5652, RFC 2268.

## Post-quantum and hybrid cryptography

Post-quantum algorithms are registry entries alongside the classical ones rather than bolt-ons, so adding one is a data row rather than a code path.

- **ML-KEM in X.509** — *Shipped.* ML-KEM public keys in certificates and PKCS#8 private keys: parse and import all three parameter sets, enforce the keyEncipherment-only key usage in path validation, and lint the certificate and encapsulation-key size against the algorithm OID. RFC 9935 / FIPS 203.
- **ML-DSA in X.509** — *Signing shipped.* `pki.x509.sign` issues an ML-DSA-44/65/87 certificate (`parameters` absent, RFC 9882 / RFC 9909 algorithm identifiers), self-signed or CA-signed, and certification-path validation verifies an ML-DSA certificate signature. Both are tracked against the LAMPS certificate specification through publication. draft-ietf-lamps-dilithium-certificates.
- **SLH-DSA** — *Verification shipped; CMS signing and verification shipped.* All twelve FIPS 205 parameter sets verify in certification-path validation (`pki.path.validate`), and `pki.cms.sign` and `pki.cms.verify` sign and verify a CMS SignedData with any of the twelve pure sets: pure mode, empty context, the parameter set's message digest pinned per RFC 9814 §4, freely mixed with the classical and ML-DSA signers. The parameters-must-be-absent rule is enforced across every format's AlgorithmIdentifier. Certificate signing is shipped: `pki.x509.sign` issues an SLH-DSA certificate in any of the twelve parameter sets, verified by OpenSSL. RFC 9909 (X.509), RFC 9814 (CMS).
- **ML-KEM in CMS** — *Shipped.* `pki.cms.encrypt` and `pki.cms.decrypt` produce and consume ML-KEM-512/768/1024 KEMRecipientInfo recipients end to end (RFC 9629 / RFC 9936), riding the FIPS 203 KEM encapsulation and decapsulation in the crypto engine, with ciphertext-size and parameters-absent enforcement. A post-quantum recipient is an OID-keyed registry row exactly like an RSA one. RFC 9629 / RFC 9936.
- **ML-DSA in CMS** — *Shipped.* `pki.cms.sign` and `pki.cms.verify` sign and verify a CMS SignedData with the post-quantum ML-DSA-44/65/87: pure mode, empty context, `parameters` absent, freely mixed with classical signers in one SignedData. The message-digest algorithm is held to each parameter set's security strength (SHA-512 by default, SHAKE256 optional), and a below-strength digest is refused on both sign and verify. RFC 9882.
- **Composite (hybrid) signatures** — *Certification-path and CMS verification shipped; CMS signing shipped.* Certification-path validation (`pki.path.validate`) verifies composite ML-DSA signatures, the transition-period construction pairing a post-quantum ML-DSA with a traditional RSA, ECDSA, or EdDSA so a certificate stays trustworthy if either primitive is later broken. All 18 draft-19 algorithm identifiers are registered under the `id-alg` arc and their AlgorithmIdentifier parameters-absent rule is enforced across every format. Verification reconstructs the domain-separated message representative, checks the ML-DSA component (with the composite Label as its context) and the traditional component independently, and accepts only when both pass; an OR would be the downgrade this construction exists to prevent. The same combinator backs a composite-signed CRL or OCSP response. Sixteen algorithm arms verify today, including the Ed448 arm whose pre-hash is SHAKE256; the two brainpool-curve arms are registered and parameters-guarded but fail closed to `path/unsupported-algorithm` at verify until their curve is reachable. Composite ML-DSA CMS `SignerInfo` signing and verification are shipped: `pki.cms.sign` and `pki.cms.verify` sign and verify a SignedData whose signer uses a composite arm, with the arm's pre-hash fixing the SignerInfo digestAlgorithm (draft-ietf-lamps-cms-composite-sigs) and both components signed and verified over the domain-separated preimage. X.509 composite certificate issuance is shipped: `pki.x509.sign` issues a certificate under a composite arm, signing both the ML-DSA and the traditional component over the certificate's `tbsCertificate`. draft-ietf-lamps-pq-composite-sigs. The sibling composite ML-KEM key establishment is shipped in `pki.kem`; see **Composite ML-KEM**.
- **Composite ML-KEM** — *Shipped (`pki.kem`).* `pki.kem.encapsulate` and `pki.kem.decapsulate` establish and recover a 256-bit shared secret with a composite ML-KEM key: a post-quantum ML-KEM hybridized with a traditional RSA-OAEP, ECDH, X25519, or X448, so the secret holds if either component is later broken. Each component KEM runs independently and the two secrets are mixed through the draft's SHA3-256 combiner, which binds the traditional ciphertext, the traditional public key, and a per-algorithm label. All twelve algorithm identifiers (ML-KEM-768 and ML-KEM-1024 with RSA-OAEP 2048/3072/4096, ECDH over P-256/P-384/P-521 and brainpoolP256r1/P384r1, X25519, and X448) are registered under the PKIX algorithm arc with their parameters-absent rule enforced, and each is verified against the draft Appendix G known-answer vectors. A composite ML-KEM public key is recognized in an X.509 SubjectPublicKeyInfo. The CMS KEMRecipientInfo binding is shipped: `pki.cms.encrypt` and `pki.cms.decrypt` envelope to and open a composite ML-KEM recipient (the composite as the `kem` algorithm, params absent, HKDF-SHA256 to an AES-256 wrap, RFC 9629 / RFC 9936), every secret-dependent fault collapsing to the uniform `cms/decrypt-failed`. draft-ietf-lamps-pq-composite-kem.
- **Stateful hash-based signatures (verify-only)** — *Shipped (HSS/LMS); XMSS Planned.* `pki.shbs.verify` and `verifyLms` verify HSS/LMS signatures (RFC 8554, carried by RFC 9802 X.509 and RFC 9708 CMS), proven against the RFC 8554 Appendix F and full NIST ACVP known-answer suites across every SP 800-208 parameter set. Pure public-input SHA-256 and SHAKE256 hashing, a data-driven typecode registry, fail-closed. XMSS and XMSS^MT verification remain *Planned*, since RFC 8391 ships no known-answer vector and NIST ACVP does not yet cover XMSS, so it awaits an authoritative interoperability vector. Automatic HSS/LMS verification inside `pki.path.validate` is likewise *Planned*, awaiting a real HSS-signed certificate to prove the path wiring end to end; operators verify today by handing the raw blobs to `pki.shbs.verify`. Signing is deliberately out of scope, because stateful-key reuse is catastrophic and belongs in an HSM. RFC 8554 / RFC 8391 / NIST SP 800-208.
- **HPKE** — *Shipped (classical DHKEM); PQ KEMs Planned.* `pki.hpke` implements the RFC 9180 base construction — `setupS` and `setupR` plus `seal`, `open`, and `export` — over the DHKEM suites P-256, P-521, X25519, and X448, HKDF-SHA256 and HKDF-SHA512, all three AEADs plus export-only, and all four modes. This is the composition ECH, MLS, and OHTTP build on, each proven against the RFC 9180 Appendix A vectors. It is pure composition over the native crypto engine, with no ASN.1. DHKEM(P-384) and HKDF-SHA384 are RFC-registered but Appendix A ships no known-answer vector for them, so they are not offered and a request fails closed until an authoritative KAT exists; both admit as a one-row registry addition then. ML-KEM and the X-Wing PQ-hybrid as HPKE KEMs likewise remain *Planned*: their HPKE bindings are specified only by moving drafts with no stable interoperability vector, so the KEM registry is shaped to admit them as a data-row addition once those specs stabilize. RFC 9180.
- **FN-DSA** — *Under design.* Registry rows and the parameters-absent treatment are reserved so the FIPS 206 lattice signature becomes a data-row addition once the standard and the runtime land. FIPS 206 (draft).
- **HQC** — *Under design.* Registry rows are reserved for the code-based KEM NIST selected in March 2025 as a second-track standard alongside ML-KEM, a hedge on different mathematical foundations (syndrome decoding rather than structured lattices) against a lattice break. Encapsulation and decapsulation and the X.509 and CMS KEMRecipientInfo bindings become a data-row addition once NIST's draft standard and a runtime implementation land. NIST PQC (draft standard forthcoming).
- **EdDSA** — *Shipped (verify).* Ed25519 and Ed448 signature verification are wired into certification-path validation with the issuer-key/signature-algorithm consistency check; X25519/X448 key agreement and EdDSA signing follow. RFC 8410 / RFC 8032.
- **KEM usage discipline** — *Shipped (core); hybrid combiners Planned.* The rules that govern how a KEM is used rather than how it is computed. Every key-establishment secret the toolkit allocates is wiped as soon as it stops being needed, on the failing path as well as the succeeding one (NIST SP 800-227 RS5 / §4.2, RFC 9629 §7): the KEM shared secret and the key-encryption key derived from it, and equally the classical ECDH / X25519 / X448 agreement secret, a KDF input keying copy, a password-derived KEK, and the content-encryption key. This is best effort, since a runtime copies buffers where no code can reach them, so it shortens the window rather than eliminating it. The ciphertext-length check FIPS 203 §7.3 requires of a decapsulating party is enforced at the crypto engine, so a caller reaching `decapsulateBits` directly gets it too, and it is a length check only: a correct-length tampered ciphertext still resolves to a pseudo-random secret, because turning implicit rejection into a throw would be a decryption oracle. Component-strength expectations (RFC 9629 §7) are reported by `pki.lint` rather than rejected at parse, since the specification states them as SHOULD and permits AES-256-KW under ML-KEM-768. The composite ML-KEM combiner is shipped in `pki.kem` (see **Composite ML-KEM**), verified against the draft's own Appendix G known-answer vectors, which are the stable interoperability oracle the HPKE release waited for. The X-Wing hybrid combiner remains *Planned*, its binding specified only by a moving draft with no such vector yet. NIST SP 800-227 / FIPS 203 / RFC 9629.
- **Additional PQC signatures (the NIST on-ramp)** — *Forward-watch.* Beyond the main-track winners, NIST is standardizing additional, mostly non-lattice signatures as a diversity hedge (SQIsign, MAYO, UOV, HAWK, FAEST, CROSS and others, in multi-round evaluation). None has an assigned OID or a drafted standard yet, and the OID-keyed registry is shaped to admit the eventual winner as a data-row addition rather than a rewrite. NIST PQC Additional Digital Signatures project.
- **Post-quantum transition timeline** — *Forward-watch.* NIST's migration guidance deprecates quantum-vulnerable RSA and ECC after 2030 and disallows it after 2035, endorsing hybrid and dual-algorithm operation through the transition. That is the deprecation clock the toolkit's PQC-first defaults and its composite and hybrid surfaces are built against, tracked so algorithm-policy gates can enforce it as the dates land. NIST IR 8547 (draft) / SP 800-131A Rev. 3 (draft).
- **Standards conformance (the shipped primitives).** The classical and hash primitives the engine already runs each map to their governing NIST standard, resolved through the same OID registry the parsers read so the compliance mapping stays data-driven: ECDSA, EdDSA, and RSA verification to **FIPS 186-5**, including the §6.4.2 reject of ECDSA r/s outside [1, n-1] that defeats the zero-signature forgery class (CVE-2022-21449), over the **SP 800-186** named curves; SHA-2, SHA-3, and SHAKE to **FIPS 180-4** and **FIPS 202**; AES-GCM to **FIPS 197** and **SP 800-38D**; HMAC to **FIPS 198-1**; the HPKE key-schedule and key-establishment KDF to **SP 800-56C**; and the shipped HSS/LMS stateful hash-based verification to **SP 800-208**.

## Revocation and transparency

- **OCSP** — *Shipped.* `pki.ocsp` is the full RFC 6960 request and response surface: `buildRequest` (one or many `{ cert, issuer }` queries, CertID under SHA-1 or SHA-2, optional RFC 9654 nonce, optional requestor signature, the RFC 5019 lightweight profile), `sign` (a signed BasicOCSPResponse over the exact ResponseData DER, from the issuing CA or a delegated responder, with good, revoked, or unknown status, under any `pki.cms.sign` algorithm including the post-quantum ML-DSA and SLH-DSA sets), `buildErrorResponse` (the unsigned §2.3 error), and `verify` (fail-closed relying-party verification: CertID binding under the CertID's own hash, responder authorization, signature over `tbsResponseDataBytes`, currency, and RFC 9654 nonce echo). Verification composes the same hardened responder-authorization, signature, and currency core as `pki.path.ocspChecker`, so there is no weaker second verify path; it is also exposed lower-level as `pki.path.verifyOcspResponse`. `verifyRequest` is the responder-side inverse of `buildRequest`: it verifies a client's signed request under the requestor certificate the request carries, trying each embedded certificate since RFC 6960 §4.1.1 certs is an unordered SEQUENCE, through the same signature engine `verify` uses, and reports whether the request was signed, whether the signature verifies, every certificate whose key verified (`signerCerts`, so a key under an expired certificate beside its renewal is not hidden behind ordering) with the first one's decoded subject, and the full embedded certificate bag (`certs`, including non-signing intermediates for path building); an unsigned request is reported with `signed: false` rather than refused, and the request bytes are snapshotted so a mutation across the async check cannot change the verdict. Both directions are cross-checked against `openssl ocsp`. RFC 6960 / RFC 9654 / RFC 5019.
- **TLS certificate compression** — *Shipped (codec).* `pki.tls.decompressCertificate` and `pki.tls.compressCertificate` are the RFC 8879 `CompressedCertificate` codec over zlib, brotli, and zstd: the compressed form of a TLS 1.3 `Certificate` message, which is the largest payload a handshake carries and the one post-quantum chains grow by kilobytes. Decompression enforces the two-sided bound RFC 8879 §5 requires. The decompressor is capped at the message's own declared uncompressed length, so a decompression bomb is refused mid-stream rather than allocated, and the recovered length must then equal that declaration exactly, which catches the under-length direction a cap cannot see. An algorithm outside the registry, one this runtime cannot decompress, or one the receiver never advertised is refused before any decompressor runs; an empty compressed body is a framing violation; and trailing bytes, after the wire message or after the compressed frame, are refused, so one chain has exactly one encoding. `pki.tls.parseCertificateMessage` decodes the RFC 8446 §4.4.2 `Certificate` message itself, surfacing each entry's certificate DER raw for `pki.schema.x509.parse` alongside its extensions; a separate extension negotiates the certificate type, so it is declared rather than inferred from the bytes. All three registered algorithms are implemented, but only those the running Node can decompress safely are offered or accepted: an algorithm whose decompressor reports a truncated frame as a short result rather than a fault is dropped at startup, because a peer could then cut a frame's tail and have the receiver process a prefix. This is the wire codec rather than a TLS stack: the toolkit decodes and produces these structures but does not negotiate the extension or speak the handshake. RFC 8879 / RFC 8446 / RFC 7250.
- **Certificate Transparency SCTs** — *Parse, verify, encode, sign, and log-list trust shipped.* `pki.ct.parseSctList` decodes the SCT-list extension to per-SCT log id, exact timestamp, named algorithm, and raw signature, preserving unknown versions opaque. `pki.ct.reconstructSignedData` rebuilds the exact digitally-signed preimage. `pki.ct.verifySct(entry, sct, logKey)` verifies an SCT's signature against a log's public key per RFC 6962 §3.2, reconstructing the signed data, routing an ECDSA signature through the shared strict DER-conformance gate before conversion to the raw form the crypto engine expects, and verifying through `pki.webcrypto`. On the producing side, `pki.ct.encodeSctList(scts)` builds the SCT-list extension value byte for byte as the exact inverse of `parseSctList`, and `pki.ct.signSct(entry, logKey)` performs a log's signing step, rebuilding the same signed-data preimage the verifier hashes and signing it with the log's ECDSA-P-256 or RSA key to yield a v1 SCT `verifySct` accepts. For trust, `pki.ct.parseLogList(json)` ingests the CT log-list JSON, the `log_list.json` browsers consume, into constraint-carrying trusted logs, recomputing each log's id as SHA-256 of its key and refusing a stated id that disagrees (a swapped key or flipped id, §3.2) and decoding the log state and temporal interval. `pki.ct.verifySctWithLogList(entry, sct, logList)` resolves the log key from the SCT's log id, enforces the state (usable, qualified, and readonly trusted; retired only before retirement; pending and rejected refused) and the temporal-interval window against the covered certificate's notAfter, then delegates the signature check to `verifySct`. `pki.ct.verifyLogListSignature(json, signature, publicKey)` verifies the detached `log_list.sig` over the raw log-list bytes against a caller-pinned signer key (RSASSA-PKCS1-v1.5/SHA-256, with an EC P-256 arm for future-proofing, and forgeable-key defenses failing closed), cross-checked against `openssl dgst -verify`, completing the offline log-list trust chain of verify-then-`parseLogList`. The live-fetch client is shipped: `pki.ct.fetchLogList(opts)` GETs the `log_list.json` and its detached `log_list.sig` over the shared `pki.transport`, verifies the detached signature over the raw fetched bytes against a caller-pinned distributor key before parsing, and only on a valid signature ingests the same bytes through `parseLogList`, returning the trusted-log set plus the surfaced `version` and `timestamp`. The caller pins the vendor URL and the key, so neither is baked in; TLS trust is explicit with `rejectUnauthorized` always on; each response is size-capped before the trust chain; and the transport is injectable for offline testing. `pki.ct.verifySctList(entry, list, logList, opts?)` lifts this to a certificate-level verdict over the whole SCT set (§3.3): it reports how many distinct trusted logs verified an SCT (so a duplicated SCT cannot inflate the count) and from how many distinct trusted operators, and whether that meets a caller's CT policy (`minScts`, `minOperators`, both defaulting to the RFC floor of one), rendering a policy shortfall as a verdict and a per-SCT failure as a recorded row. `pki.ct.x509CertEntry(cert, issuer)` reconstructs the precertificate log entry from a final certificate by byte surgery on its TBSCertificate, and `pki.path.validate` accepts an optional `ctLogList` / `ctPolicy` gate that runs that verification as part of path validation, failing closed on a policy-declaring certificate that carries no SCTs. RFC 6962.
- **Merkle transparency proofs** — *Proof core shipped; envelope under design.* The RFC 6962 / RFC 9162 inclusion and consistency proof-verification core shipped as `pki.merkle`: `leafHash`, `nodeHash`, and `emptyRootHash` plus `verifyInclusion` and `verifyConsistency`, fail-closed with a constant-time root compare over sync SHA-256, transport-free. The C2SP checkpoint, signed-note, and tile envelope layer — the static-CT-API tiled-log parsing that feeds proofs into this core — remains under design. One core serves a static-CT log client, Merkle Tree Certificate verification, transparency-log inclusion proofs, and the shipped SCT surface. RFC 6962 / RFC 9162; C2SP static-ct-api / tlog-tiles / tlog-checkpoint.
- **Merkle Tree Certificates** — *Under design.* Verification of the post-quantum-oriented certificate format, compact and transparency-log-anchored, that major CAs and browsers are piloting, composing the Merkle-proof core. draft-ietf-plants-merkle-tree-certs.
- **Partitioned / sharded CRLs** — *Shipped.* The `cRLDistributionPoints` and `freshestCRL` extension decoders plus the RFC 5280 §6.3.3 Distribution Point to Issuing Distribution Point correspondence in `pki.path.crlChecker`: a partitioned CRL whose critical IDP shares an identically encoded name with one of the certificate's distribution points, carries no reason restriction, is current, and verifies, establishes non-revocation for its shard. Non-corresponding, reason-restricted, or unverifiable shards fail closed to undetermined, and a listed serial reports revoked regardless. Reason-shard mask accumulation across corresponding distribution points and delta-CRL merge onto the complete CRL are shipped (see **CRLs** above). RFC 5280 §5 / §6.3.
- **Trust-store ingestion (`pki.trust`)** — *Shipped.* `pki.trust.parseCertdata` and `parseCcadbCsv` ingest the Mozilla/NSS `certdata.txt` object stream and the CCADB certificate-records CSV into constraint-carrying trust anchors, carrying the per-purpose trust bits (only a trusted delegator grants a purpose) and the distrust-after dates the bare root list omits, and `pki.path.validate` enforces them via `opts.checkPurpose` (`path/distrusted-after`, `path/purpose-not-trusted`). The CCADB per-root name-constraint overlay and live fetching remain *Planned*.

## Timestamping — RFC 3161

- **Time-Stamp Protocol** — *Shipped.* `pki.tsp.sign(messageImprint, tsa, opts)` creates an RFC 3161 TimeStampToken: a CMS SignedData over `pki.cms.sign` whose content is a `TSTInfo` carrying the message imprint, TSA policy, serial number, and `genTime` with optional accuracy, nonce, and ordering, plus the RFC 3161 §2.4.2 / RFC 5816 signing-certificate (ESSCertIDv2) attribute binding the token to the TSA certificate. `pki.schema.tsp.parseToken` decodes one. `pki.tsp.request` and `pki.tsp.parseRequest` build and parse the `TimeStampReq` a client sends (message imprint, requested policy, nonce, certReq), and `pki.tsp.response` and `pki.tsp.parseResponse` build and parse the `TimeStampResp` a TSA returns, either a granted status wrapping a token or a rejection carrying a PKIStatus and failure info, with the §2.4.2 status-to-token coupling enforced in both directions. `pki.tsp.verify(token, data, opts)` verifies a token: the CMS signature over the exact signed bytes, the message imprint recomputed from the original data, the id-ct-TSTInfo content type, the ESSCertID(V2) binding of the token to the TSA certificate, the §2.3 requirement that the TSA certificate carry a critical extendedKeyUsage of exactly id-kp-timeStamping, the request nonce when one was used, and, when a trust anchor is supplied, full certification-path validation of the TSA certificate at the token's `genTime`. A well-formed token failing any check is a fail-closed `{ valid: false }` verdict with a typed reason code. This is a message layer rather than an HTTP client: the builders emit the byte payloads the RFC 3161 §3 transports carry. RFC 3161 / RFC 5816.

## Attribute certificates — RFC 5755

- **Attribute certificates** — *Shipped (v2 parse, value decoding, issuance, and validation).* `pki.schema.parse` detects and decodes an RFC 5755 v2 attribute certificate: the `AttributeCertificateInfo` (holder, issuer, validity, attributes, extensions), the signature algorithm, and the signature, surfacing the raw `acinfo` bytes a signature verifier hashes. The RFC 5755 §4.4 attribute values (role, clearance, service-authentication and access identity, group, charging identity) and §4.3 extensions (audit identity, target and proxy information, no-revocation-available, AA controls) are decoded to structured values additively, as a `decoded` field alongside the raw bytes, with every embedded GeneralName validated, an unrecognized type preserved opaque, and a malformed recognized value failing closed. The obsolete v1 profile is recognized and declined with a typed error. `pki.attrcert.sign(spec, issuer, opts)` issues a v2 attribute certificate: a holder in any of its four forms (entity name, base certificate ID, a certificate to derive it from, or an object digest), the AA issuer, a validity window, the §4.4 attribute values, and the §4.3 extensions, signed with any registry algorithm including the post-quantum and composite sets, with the produced signature verified under the AA public key before the certificate is returned. `pki.attrcert.verify(ac, issuer, opts)` is the receiving side: it performs the RFC 5755 sec. 5 checks an attribute certificate and a named issuer can settle between them -- the signature over the exact acinfo bytes through the one path-validation signature engine, the AC naming the issuer this verifier trusts, the evaluation instant lying within the validity with equality at either bound succeeding as the section states, the sec. 4.3.2 targeting rule, and rejection of any critical extension this build cannot parse. The holder's own certificate chain and the AC issuer's chain need certificates the verb is not given, so the verdict reports those as unchecked rather than letting their absence read as a pass. RFC 5755.

## Enrollment and lifecycle protocols

Certificate lifecycle management is a first-class goal of this toolkit rather than a layer left to the application.

- **ACME** — *Shipped.* `pki.acme.client(directoryUrl, opts)` is a stateful RFC 8555 client that drives a live CA directory over `pki.transport`: fetch the directory, register or find an account, place an order, answer its authorizations, finalize with a CSR, and download the issued chain. It adds single-identifier pre-authorization (`newAuthz`, §7.4.1), an opt-in badSignatureAlgorithm re-sign under caller-approved alternative account-key algorithms (`opts.resignKeys`, §6.2, downgrade-resistant per §10), alternate-chain selection in `downloadCertificate` (`Link rel="alternate"`, §7.4.2), `revokeCert` (§7.6, account-key or certificate-key signed), `keyChange` (§7.3.5 account key rotation), account and authorization deactivation, account contact update (`updateAccount`, §7.3.2) and orders listing (`listOrders`, following the §7.1.2.1 `Link rel="next"` pagination), ARI `renewalInfo`, and the `renewalWindow` renewal decision (RFC 9773 §4.2/4.3). It owns only session state — the fetched directory, the single-use nonce pool, the account URL as the `kid` — and is fail-closed: HTTPS is required for the directory and every server-returned URL, the default transport needs an explicit trust anchor, each request carries a fresh nonce with a bounded badNonce retry, reads are POST-as-GET, a poll count and a total-wait budget bound the polling, which sleeps on a Retry-After via an injectable sleeper, and every response body is size-capped. `downloadCertificate` binds the certificate that comes back to the order that was placed, in both directions of the exchange: the CSR's identifier set must equal the order's on the way out (§7.4), and the returned end-entity certificate must certify the key that CSR asked to have certified (`expectedSpki`) and carry the order's own identifiers (`identifiers`) on the way in. At least one of the two is required by default, so a caller holding only the order or only the CSR can still bind what it has, and the result reports `boundToKey` / `boundToIdentifiers` so a binding that was not performed cannot read as one that was. A certificate's identifiers are its dNSName and iPAddress subject alternative names, its common name read only where it asserts none, while the CSR check reads every common name the request carries — the one says what a certificate authenticates, the other what the request asks to have certified. A name that maps to no order identifier is refused rather than dropped from the comparison, and names fold under ASCII case rules rather than the Unicode mapping. Under it sits the message layer it composes, updated by RFC 8737 tls-alpn-01, RFC 8738 IP identifiers, and RFC 9773 ARI, over the `pki.jose` JWS surface: resource-object validators (closed status enums, conditional-required fields, unknown fields ignored), the three §7.1.6 state machines, the request builders (newAccount with External Account Binding, newOrder with `replaces`, finalize with CSR identifier-set match and account-key-reuse rejection per §11.1, challenge responses, deactivation, revokeCert in both key modes, the keyChange nested JWS, POST-as-GET), the http-01 / dns-01 / tls-alpn-01 challenge computations, the dns and ip identifier validators, and the ARI certID with serial sign-padding preserved. The transport stays injectable and every codec is fail-closed. An auto-sleeping renewal scheduler is *Planned*; `renewalWindow` surfaces the RFC 9773 renewal decision as data — the selected time, whether to renew now, and a clamped Retry-After — so an operator drives the timer today. RFC 8555 / RFC 8737 / RFC 8738 / RFC 9773.
- **JOSE** — *Shipped.* `pki.jose` is the RFC 7515 Flattened JWS and RFC 7638 JWK-thumbprint layer ACME composes: a strict base64url codec, a bounded duplicate-member-rejecting JSON reader, profiled `sign` and `verify`, an algorithm registry spanning ES/RS/PS/EdDSA/ML-DSA that binds each `alg` to its key type, and canonical thumbprints (RFC 8037 OKP, RFC 9964 AKP). RFC 7515 / RFC 7518 / RFC 7638 / RFC 8037 / RFC 9964.
- **EST** — *Shipped.* `pki.est` is a working Enrollment over Secure Transport client (RFC 7030, updated by RFC 8951 and RFC 9908). The network verbs `cacerts`, `simpleenroll`, `simplereenroll`, `serverkeygen`, `csrattrs`, and `fullcmc` drive the flow over `pki.transport`: HTTPS-only, an explicit trust anchor required, same-origin redirects followed while a downgrade or loop is refused, HTTP Basic or Digest answered only after the server is authenticated and dropped across an origin boundary, a 202 Retry-After surfaced rather than slept on, and the issued certificate chosen by public-key match. `serverkeygen` requests a server-generated key pair, with the key part surfaced cleartext or as an opaque CMS EnvelopedData, its encryption bound to the CSR's own key-identifier attribute, over a confidentiality-bearing cipher. `csrattrs` fetches the CA's RFC 9908 CSR-attributes policy, where a 204 or 404 is a valid "none available". HTTP Digest access authentication (RFC 7616, SHA-256 and SHA-512-256; MD5 and no-qop refused by default) is available on every verb as an alternative to Basic. Under them sit the transport-agnostic codecs they compose: the base64 transfer codec, which ignores Content-Transfer-Encoding; the `multipart/mixed` splitter; the certs-only and serverkeygen response validators over the CMS parser; the enroll-attribute builders (out-of-band key identifiers, SMIMECapabilities, the RFC 9908 template-priority plan); and the HTTP response classifier. Channel binding is partial: `challengePasswordFromTlsUnique` encodes RFC 5929 tls-unique bytes into the RFC 7030 §3.5 challengePassword, and a server instruction to include one is surfaced as `channelBindingRequired`, but the toolkit does not produce the tls-unique value. The caller must source it from the live TLS socket, which `pki.transport` does not currently expose, so the attribute cannot be driven end to end through the shipped verbs. Surfacing it from the transport is *Planned*. Its companion `pki.schema.csrattrs` parses the CSR Attributes wire format (RFC 8951 §3.5 / RFC 9908). `fullcmc` completes the verb set: it POSTs a Full PKI Request built by `pki.cmc.build` and returns the `pki.cmc.verify` verdict, accepting either response arm RFC 7030 §4.3.2 names (`certs-only` or `CMC-response`, with the label required to agree with the bytes), treating a 404 or a 501 as the distinct "not implemented" answer, and surfacing the CMC verdict a rejection must carry as a typed `est/cmc-failed`, without ever letting an unreadable error body mask the HTTP fault it arrived with. RFC 7030 / RFC 8951 / RFC 9908 / RFC 7616 / RFC 5272.
- **HTTP transport** — *Shipped.* `pki.transport` is the shared, fail-closed `node:https` transport the enrollment clients drive: `pki.transport.https(defaults)` returns a `transport(request) → { status, headers, body, tls }`, the `tls` field carrying the negotiated `protocol`, `cipher`, and raw `peerCertificate`. It is the toolkit's single socket choke point, with TLS server authentication always on and no disable path, an explicit trust anchor (or a system-store opt-in) required, TLS floored at 1.2, the response body capped while it streams, and a stalled socket timing out. It carries no protocol semantics, so the EST, ACME, CMP, and CT clients reuse it verbatim. An injected transport should surface `tls` as well: `pki.est.serverkeygen` asserts the negotiated cipher is confidentiality-bearing before it hands back a server-generated private key, and a transport reporting no cipher is trusted rather than refused, so a substitute that omits the field skips the assertion.
- **Certificate request messages (CRMF)** — *Parse, build and proof-of-possession verification shipped.* `pki.schema.crmf.parse` decodes an RFC 4211 CertReqMessages, the request body CMP and EST enrollment carry, into the requested-certificate template, proof of possession, and registration controls, surfacing the raw CertRequest bytes a proof-of-possession verifier hashes. `pki.crmf.build` assembles one: a CertTemplate of the requested certificate fields plus a POPOSigningKey proof of possession signed with the private half of the requested key, or a raVerified proof, across every signature algorithm the registry resolves, carrying requested extensions, registration controls, and regInfo, in a single message or a batch. A key that cannot sign, which is where an ML-KEM enrollment sits, uses the POPOPrivKey arms of RFC 4211 sec. 4.2 and sec. 4.3 instead: `subsequentMessage` declares whether an encrypted certificate or a challenge completes the proof over the enrolling protocol's next exchange, and `encryptedKey` encloses the requester's private key for the certification authority in a CMS EnvelopedData under `id-ct-encKeyWithID`, carrying the identifier sec. 4.2.1 makes mandatory. The enclosed key is derived and compared against `certTemplate.publicKey` before the message is built, since a proof over any other key demonstrates possession of something the request never asked to have certified. The two alternatives the specification deprecates as it defines them, `thisMessage` and `dhMAC`, are refused with their successors named, and a CMP request carrying an `encryptedKey` proof announces cmp2021(3) as RFC 9810 sec. 5.2.8.3 requires. The `agreeMAC` arm is *Planned*: it needs the RFC 2875 static Diffie-Hellman shared secret against a certification authority certificate the requester already holds. `pki.crmf.verifyPop` answers the receiving side's question about a message someone else produced: for each CertReqMsg it verifies the POPOSigningKey signature over the bytes RFC 4211 sec. 4.1 names, through the one path-validation signature engine, and reports the raVerified, keyEncipherment and keyAgreement arms as unverified with the reason no answer is available from the message alone. `pki.cmp.build` wraps them in the CMP `ir` / `cr` / `kur` request body.
- **CMP** — *Parse and build shipped.* `pki.schema.cmp.parse` decodes an RFC 9810 PKIMessage, the protected transport envelope CMP enrollment, revocation, confirmation, and support exchanges ride, into its header, its 27-arm body (certificate requests via the CRMF parser, encrypted certificates via CMS, response / revocation / confirmation / error / support / polling arms structural, the rest raw), protection inputs, and extra certificates, surfacing the exact byte slices an external verifier reconstructs the protected part from. `pki.cmp.build` assembles a protected PKIMessage: a header (sender and recipient, including the anonymous NULL-DN, plus transaction metadata) and a single-arm body across both directions — request-side `ir` / `cr` / `kur` (a CertReqMessages via `pki.crmf.build`), `p10cr` (a PKCS#10 CertificationRequest), `certConf`, `pollReq`, `genm`, and `rr`; and CA or responder-side `ip` / `cp` / `kup` / `ccp` (a CertRepMessage of CertResponse entries, each a PKIStatusInfo and, under a granting status, a certifiedKeyPair), `rp` (revocation response), `genp`, `error`, `pollRep`, `krp` (key-recovery response), and `pkiconf`. Protection is a sender-key signature, resolved from the signer certificate over any registry algorithm, or a PBMAC1 shared-secret HMAC (RFC 9481 / 9579), computed over the exact ProtectedPart DER. The protectionAlg is derived rather than caller-set, and the protection self-verifies before the message is returned, so every message round-trips through the parser. A `p10cr` request's PKCS#10 proof-of-possession is verified before the message is protected, so one whose self-signature does not verify under its subject public key is refused rather than sent. `pki.cmp.transfer(url, message, opts)` carries a built PKIMessage to a CMP endpoint over the shared `pki.transport` (RFC 9811 HTTP transfer): one POST of the DER message, with the response classified fail-closed — a 200 with an `application/pkixcmp` body parsed; a non-200 2xx or an un-followed 3xx refused; a 4xx or 5xx carrying a CMP error PKIMessage forwarded as the integrity-protected verdict, with the HTTP status surfaced as data and never setting the verdict; a 4xx or 5xx with no CMP body an error — and protection surfaced rather than verified. `pki.cmp.wellKnownUrl` builds the RFC 9811 §3.4 `/.well-known/cmp` request-URIs. Incoming protection verification is shipped: `pki.cmp.verify(message, opts)` verifies a signature or PBMAC1 `PKIProtection` over the exact `ProtectedPart` of an incoming `PKIMessage`, reconstructed from the parser's raw header and body wire slices rather than a re-serialization. The protection flavor is read from `protectionAlg` alone, the signature is checked through the same certification-path signature engine `pki.crl.verify` and `pki.ocsp.verify` use, with the EdDSA low-order-point and algorithm-confusion gates, and the MAC is recomputed from the caller's shared secret and the message's own PBKDF2 parameters and compared in constant time. It fails closed on an unprotected message, a legacy or KEM MAC algorithm, an omitted keyLength, a SHA-1 PRF, or a work factor over the cap; binds the authenticated header `sender` field to the signer certificate subject (RFC 9483 §3.1); and, given a trust store, fully path-validates the signer certificate (RFC 5280 §6.1 plus the RFC 9483 §3.2 `keyUsage.digitalSignature` gate) at a trusted current time before reporting the signer trusted, surfacing the signer certificate for the caller to anchor when no trust store is supplied. Opt-in `transactionID` and `recipNonce` echo checks defend a matched exchange. A protection-verified message is held to the RFC 9483 §3.5 receiving-side header rules: the `pvno` must be cmp2000(2) or cmp2021(3) (a cmp1999(1) message stays valid RFC 9810 syntax the parser decodes, refused only on receipt), the `transactionID` must be present, and the `senderNonce` must be present and carry at least 128 bits, each a fail-closed verdict. The stateful enrollment orchestrator is shipped: `pki.cmp.session(opts)` composes `build`, `transfer`, and `verify` into a single `session.enroll(request)` that drives an `ir` / `cr` / `kur` / `p10cr` transaction to completion. It mints one stable `transactionID` and a fresh `senderNonce` per request, echoing the peer's last `senderNonce` back as `recipNonce` (RFC 9810 §5.1.1), verifies every response's protection and binds it to the exchange before reading the body, polls a `waiting` status under a bounded `pollReq`/`pollRep` loop with an injectable sleeper capped by a poll count and a total-wait budget, and confirms a grant with a `certConf`/`pkiConf` handshake unless implicit confirmation was granted, detected from the granting response's own header including after polling. A verified rejection or error, or a poll-budget timeout, is a terminal typed verdict (`outcome`: `issued`, `rejected`, `poll-timeout`); a tampered, unverifiable, or desynchronized response is a hard-stop `CmpError`. Signature (`opts.key` plus `opts.cert`) or PBMAC1 (`opts.mac`) protection drives the identical transaction. The same session drives the other two operations of the lightweight profile under that shell. `session.revoke(request)` sends an `rr` naming a certificate as `{ certificate }` or `{ certDetails: { issuer, serialNumber } }` with an optional CRLReason `reason`, always carrying the reasonCode the profile requires even at `unspecified(0)`, and reaches `revoked`, `rejected`, or `poll-timeout`. Because the signature over the request is the proof of authorization to revoke (§4.2), the named certificate must be the one the session protects with, compared by serial number and by the RFC 5280 §7.1 canonical name rule, and a PBMAC1 session is refused. `session.info(request)` sends a `genm` for one of the four support messages — the available CA certificates, a root CA key update, the certificate-request template, or a CRL from a named issuer, optionally narrowed to a distribution point — and returns `answered` with the decoded value and a `present` flag distinguishing a value from the absence that means nothing is available. Each response is held to its profile shape before its content is read: one status on an `rp` with no `failInfo` under an accepted one, no `failInfo` on a waiting `ip`/`cp`/`kup` CertResponse (§4.4), one `InfoTypeAndValue` on a `genp` carrying the identifier that operation is answered with, and a certificate-request template that omits `publicKey`, `serialNumber`, `signingAlg`, `issuerUID`, and `subjectUID`. A root key update is held to the relationships §4.3.2 names rather than to field presence: `newWithOld` must carry the new root key, name the same subject as `newWithNew`, and be signed by the old root the request named, and `oldWithNew`, when sent, must carry the old root key, name the old root, and be signed by the new root, each signature checked through the certification-path signature engine and each of the three certificates required to hold the authority the update transfers (`basicConstraints` `cA` TRUE, and a `keyUsage`, where present, allowing `keyCertSign`). A CRL answer is held to the source the request named: to the issuer under the §7.1 rule, and, where the request named a distribution point and the CRL states its own scope in `issuingDistributionPoint`, to that point under the RFC 5280 §6.3.3 correspondence the path validator applies to a shard CRL. A request naming a distribution point names the issuer too, and the distribution point is the alternative sent (`CRLSource` is a CHOICE) while the issuer binds the answer; a distribution point on its own is refused, since a complete CRL states no scope to hold it to. Delayed delivery for these two arrives as an error message carrying the `waiting` status (§4.4) and drives the same bounded poll loop. The registration-authority `nested` body is shipped: `pki.cmp.build` wraps an array of complete PKIMessage DER as a `NestedMessageContent` (RFC 9810 §5.1.3.5) under the `[20]` PKIBody tag, the message a registration authority sends to forward or batch messages other parties protected; each entry is checked to parse as a PKIMessage and forwarded unchanged, and an empty array or an entry that does not parse is refused with `cmp/bad-input`. The `krr` (key recovery) request body is shipped: `pki.cmp.build` assembles it as a `CertReqMessages` under PKIBody `[9]`, identical in syntax to an initialization request (RFC 9810 §5.3.7). The `ccr` (cross-certification) request body is shipped: `pki.cmp.build` assembles it as a `CertReqMessages` under PKIBody `[13]` (RFC 9810 sec. 5.3.11), refusing the private-key-transport encryptedKey proof-of-possession since a ccr does not send the requesting CA's private key. It is a `CertReqMessages` at the sec. 5.3.11 normative floor: Appendix D.6 is an optional profile, so no D.6 template field is required and the D.6 single-request cardinality is not enforced (a multi-request ccr builds). Resuming a poll across a process restart remains *Planned*. The private-key-transport and KEM protection flavors and the remaining lightweight-profile validation rules are *Planned*. RFC 9810 / RFC 9483 / RFC 9481 / RFC 9811.
- **SCEP** — *Client codec and HTTP verbs shipped.* `pki.scep.build` and `pki.scep.parse` are the RFC 8894 pkiMessage layer a SCEP client enrolls over. A request (`PKCSReq` or `RenewalReq`) wraps a PKCS#10 certification request in two nested CMS layers: the inner EnvelopedData (`pkcsPKIEnvelope`) encrypts the request to the CA under AES-128-CBC with RSAES-OAEP key transport, and the outer SignedData signs it under the transaction attributes of RFC 8894 §3.2, a messageType, a caller-unique transactionID, and a 16-byte senderNonce. A `CertPoll` wraps an IssuerAndSubject, and a `GetCert` or `GetCRL` an IssuerAndSerialNumber, in the same two layers. The key is transported under RSAES-OAEP rather than the legacy RSAES-PKCS1-v1_5, so the CA must support OAEP. `pki.scep.parse` reads a PKCSReq, RenewalReq, CertPoll, GetCert, GetCRL, or CertRep back, refusing a messageType outside the RFC 8894 registry. It verifies the outer signature first and refuses a message whose signature does not check, so the transaction attributes it returns are read only from a verified signer and are never surfaced alongside a false verdict. Those attributes are the messageType, transactionID, pkiStatus, failInfo, failInfoText, and the sender and recipient nonces. Given the recipient key it decrypts the pkcsPKIEnvelope to the messageData, and it checks the senderNonce echo a matched exchange needs. It reads a CA's CertRep response in full, including the issued certificates a SUCCESS carries and the failInfo a FAILURE reports. `pki.scep.getCACaps`, `pki.scep.getCACert`, `pki.scep.getNextCACert`, `pki.scep.enroll`, `pki.scep.renew`, `pki.scep.getCert`, and `pki.scep.getCrl` carry that codec to a live CA over HTTP (RFC 8894 §4) through an injectable transport (`pki.transport.https` by default). `getCACaps` reports the CA's advertised capabilities and never lowers the client's algorithm choice on them, since the response is unauthenticated; `getCACert` retrieves the CA certificate and pins it to an out-of-band fingerprint the returned certificate must match; `getNextCACert` retrieves the CA's next (rollover) certificate and authenticates the response against the current CA certificate the caller holds before returning it; `enroll` and `renew` POST a PKCSReq or RenewalReq, authenticate the CertRep against the CA certificate and its nonce echo, select the issued certificate by public-key match, and poll a PENDING response with CertPoll requests until the CA answers or a bounded poll-count and total-wait budget is spent. `getCert` and `getCrl` retrieve an already-issued certificate or a CA CRL by issuer and serial number; RFC 8894 §2.6, §2.7, and §3.3.4 recommend these queries only where HTTP certificate-store access (RFC 4387), LDAP, or a CRL distribution point is unavailable, and the verb docstrings carry that guidance. `pki.scep.build` also issues the CA-side `CertRep` response (RFC 8894 §3.3.2): a SUCCESS envelopes a certs-only SignedData of the issued certificate (or the CRL for a GetCRL) to the requester and signs it under the CA key; a FAILURE carries a failInfo and a PENDING carries neither, both signed detached with the pkcsPKIEnvelope omitted, and each echoes the request's senderNonce as recipientNonce. The strong RFC 8894 profile is the default: AES-128-CBC content encryption and SHA-256. GET-carried PKIOperation and HTTP proxy authentication are *Planned*. RFC 8894.
- **CMC** — *Shipped.* Certificate Management over CMS, for federal and PIV ecosystems. `pki.schema.cmc` reads the message layer: a Full PKI Request (`PKIData`) or Full PKI Response (`PKIResponse`) carried as the encapsulated content of a CMS SignedData or AuthenticatedData, reached by content type (`id-cct-PKIData` / `id-cct-PKIResponse`). Controls are surfaced in wire order with raw values so an unrecognized one is data rather than a fault; all three tagged-request arms (PKCS#10, CRMF, other) decode; the status verdicts come back as an ordered list with the RFC 6402 two-module `OtherStatusInfo` ambiguity resolved by inspection and refused when genuinely ambiguous; body-part identity is unique across the whole message, covering controls, requests, content infos, and other messages alike; and the `reqSequence` bytes are surfaced exactly as they arrived so an Identity Proof witness is computed over the wire bytes. On top of it, `pki.cmc.verify` interprets a Full PKI Response into one terminal outcome — `issued`, `pending`, `confirm-required`, `pop-required`, or `rejected` — after binding the exchange: the Transaction Identifier, the Sender and Recipient Nonce echo (constant-time and by full value, so a truncation cannot match), and the Data Return echo, each applying only if the client sent that half and each a refusal once it did. `bodyPartIDs` carries the same rule to what the response reports on: a status naming a body part the request never sent is refused, which the transaction and nonce cannot catch. Several status controls are permitted and the worst governs, so a failure cannot hide behind an earlier success, and no status control at all is success. Both accepted carriers work, including the certificate bag an AuthenticatedData keeps under `originatorInfo`. Nothing is trusted: the certificate bag and any Publish Trust Anchors control are surfaced as data for `pki.path.validate`. `pki.cmc.build` is the producing side. It assembles a Full PKI Request across all three request arms (PKCS#10, CRMF, other), allocates body-part identifiers unique across the whole message and never the reserved 0, refusing a caller's clash rather than renumbering it since a control may already reference the identifier, and signs through `pki.cms.sign` under `id-cct-PKIData`. A PKCS#10 (`tcr`) request is verified against its own proof-of-possession before signing, so one whose self-signature does not verify under its subject public key is refused rather than signed into a message a CA would reject. An Identity Proof V2 witness is computed over the `reqSequence` bytes exactly as emitted (§6.2.1 step 1) rather than over a re-serialization; a POP Link Witness is emitted only together with the POP Link Random control §6.3.1.1 requires alongside it; and a renewal carries neither Identification nor Identity Proof, in either version. `pki.est.fullcmc` carries the exchange over the wire. Four items are deferred with written re-open conditions: the Encrypted/Decrypted POP challenge flow (decode ships; RFC 5274 §4.2 note 4 makes it conditional), the RA-side controls (decode ships; §4.2 marks them N/A for an end entity), AuthenticatedData-wrapped requests (decode ships; the producer emits SignedData), and an automated pending-to-confirm session loop, for which the response surfaces `pendToken`, `pendTime`, and `confirm-required` as data so an operator drives it. RFC 5272 / 5273 / 5274 / 6402.

## Messaging

- **S/MIME** — *Signing, verification, encryption, and compression shipped* (`pki.smime`), over the shipped ESS attribute decoders (`pki.schema.smime`). `pki.smime.sign(content, signers, opts)` assembles a signed S/MIME message in both RFC 8551 forms: `multipart/signed`, clear-signed with a detached CMS signature alongside the readable content, and `application/pkcs7-mime; smime-type=signed-data`, opaque. `pki.smime.verify` unwraps and verifies both, recomputing over the same RFC 8551 §3.1.1 canonicalizer the signer used (a shared `lib/mime.js`), so a transport that re-wraps line endings still verifies and a tampered part fails. `pki.smime.encrypt(content, recipients, opts)` envelopes a MIME entity as an opaque `application/pkcs7-mime` message and `pki.smime.decrypt` opens one, as `smime-type=authEnveloped-data` (AES-GCM, confidentiality and integrity, the default) or `smime-type=enveloped-data` (AES-CBC, confidentiality only, so `decrypt` reports `authenticated: false`, the §3.3 no-integrity caveat); the `smime-type` is derived from the CMS body rather than the header. The crypto is entirely `pki.cms.sign` / `verify` / `encrypt` / `decrypt`, so any RSA, RSASSA-PSS, ECDSA, EdDSA, ML-DSA, or SLH-DSA signer and any RSA-OAEP, ECDH, X25519, X448, AES-KW, PBKDF2, or ML-KEM recipient carries through. Decryption is fail-closed and oracle-free, and the layer is bidirectionally interoperable with `openssl smime` and `openssl cms`. `pki.smime.compress` and `pki.smime.decompress` add the opaque `application/pkcs7-mime; smime-type=compressed-data; name=smime.p7z` frame (RFC 8551 §3.6) over the CMS CompressedData layer, a size transform with no integrity or confidentiality (§2.4.5), bounded against a decompression bomb. The RFC 5035 SigningCertificate(V2) and SMIMECapabilities signed-attribute decoders surface a SignerInfo's signing-certificate binding and capability list. Header protection is shipped (RFC 9788): `pki.smime.sign` and `encrypt` gain `opts.protectHeaders`, which inlines the caller's `opts.headers` on the Cryptographic Payload root (its Content-Type gaining `hp="clear"` for a signed message or `hp="cipher"` for an encrypted one) so the CMS signature or encryption covers them, and `verify` and `decrypt` surface the authenticated inner set as `protectedHeaders` plus `headerProtection { present, mode, fromMismatch, confidential }`. Encryption applies a Header Confidentiality Policy — `hcp_baseline` obscures the outer Subject to `[...]` and removes Comments and Keywords — so the real values live only in the ciphertext, and embeds the authenticated `HP-Outer` records (RFC 9788 §2.2) documenting which fields were left visible, so `decrypt` reports which headers were kept confidential in `headerProtection.confidential` and a caller can reply or forward without leaking them (§6.1). Every emitted header routes through a header-injection guard, and a malformed or contradictory `hp` wrap fails closed (`smime/bad-header-protection`). The legacy RFC 8551 `message/rfc822` (RFC8551HP) wrap is not generated, which RFC 9788 §4.10 forbids. Inbound legacy RFC8551HP detection is shipped: `verify` and `decrypt` with `opts.legacyHeaderProtection` recognize a legacy `message/rfc822`-wrapped payload by the RFC 9788 §4.10.1 four-condition identification and surface the inner message's headers under `headerProtection.legacy = { headers, mode, fromMismatch, confidential }`, where `headers` is an ordered `[{ name, value }]` array retaining legally repeated fields such as `Received`, the mode is inferred from the envelope (`clear` signed, `cipher` encrypted), and the confidential set is derived from the actual visible outer headers. Because a legacy message is structurally indistinguishable from an ordinary forwarded `message/rfc822`, the inference is surfaced only under `headerProtection.legacy`, never in `protectedHeaders` and never setting `present: true`, so a consumer keying trust off the authenticated set is never misled and consuming it is an explicit opt-in choice. It is off by default, and a nested crypto layer, an inner `hp=`, a non-`message/rfc822` payload, or a duplicate Content-Type reports `legacy: null`. RFC 8551, RFC 5083, RFC 5035, RFC 3274, RFC 9788.

## Attestation and supply chain

Attestation chains are a growing consumer of path validation, and this section covers the ones the toolkit verifies natively.

- **WebAuthn / passkey** — *Shipped (registration and authentication verification).* `pki.webauthn.parseAttestationObject` decodes the attestation object, authenticatorData, and COSE credential key over the strict `pki.cbor` codec, and `pki.webauthn.verify` cryptographically verifies each defined attestation-statement format (packed, tpm, android-key, apple, fido-u2f, none), checking the signature and each format's structural bindings — the x5c leaf key, the apple nonce, the tpm `certInfo` Name and `extraData` over the `pubArea`, the android `KeyDescription`, the fido-u2f `verificationData` — binding every attestation certificate key to the credential key, and enforcing each leaf's certificate requirements. The credential-key evaluation covers the full WebAuthn COSE algorithm set including the RFC 9864 fully-specified identifiers (ESP256/384/512, Ed25519) and Ed448, validates the public-key point on-curve, rejects the compressed EC point form, and requires a minimally encoded DER ECDSA signature. It is verified against the official W3C WebAuthn Level 3 test-vector suite and captured attestations across every format. `pki.webauthn.verifyMetadataBlob` reads a FIDO Metadata Service (MDS v3) BLOB, the signed catalogue of registered authenticator models, verifying its JWS and chaining its signer to an operator-supplied FIDO root before the payload is parsed, and enforcing the sequence-number rollback and `nextUpdate` freshness checks. Passing the result as `opts.metadata` to `verify` resolves the authenticator's registered attestation roots from its identifier and requires the trust path to fully validate to one of them, so an unlisted, revoked, or otherwise disqualified model is refused rather than reported as verified. Both of the catalogue's key spaces are covered: an authenticator's aaguid, and, for a U2F authenticator which declares none, the key identifiers of its attestation certificates. No FIDO root ships with the toolkit and there is no trust-on-first-use. Retrieving the BLOB is out of scope, since it is caller-supplied bytes. The authentication half is `pki.webauthn.verifyAssertion`, which verifies an assertion signature over `authenticatorData || SHA-256(clientDataJSON)` — raw bytes with no COSE_Sign1 wrapper, an ES256 signature carried as ASN.1 DER, read with the same order-aware reader the attestation path uses — and applies the §7.2 step 21 counter rule against a stored `previousSignCount`, refusing a counter that fails to advance as the cloned authenticator it signals. `pki.webauthn.parseAuthenticatorData` reads the bare form an assertion carries, and `pki.webauthn.parseClientData` decodes the clientDataJSON that no signature check looks inside, returning the challenge decoded and refusing a response from the other ceremony. Both `verify` and `verifyAssertion` accept that JSON directly and apply the ceremony-type rule unconditionally, and both the framed and top-level origins of a cross-origin ceremony can be compared. What the toolkit verifies is a signature; what makes a response acceptable is the ceremony binding. The verdict fields are therefore `attestationVerified` and `signatureVerified` rather than a bare `verified`, the RP ID, user-presence, user-verification, and algorithm bindings are checked when the caller states them, and `bindingChecked` reports which ones ran. W3C WebAuthn Level 3, RFC 9864, FIDO Metadata Service v3.0.
- **Sigstore / provenance verification** — *Shipped (offline bundle verification).* `pki.sigstore.verifyBundle` verifies a Sigstore bundle, the `npm publish --provenance` artifact, offline against caller-pinned trust: the DSSE signature over its PAE under the Fulcio leaf key, the ephemeral Fulcio chain validated as of the Rekor log time through the toolkit's own path validator, the RFC 9162 inclusion proof folded to a Rekor-signed root through the Merkle-proof core, the log entry bound to this exact signature, and the in-toto SLSA subject digest, with no dependency tree of its own. The sigstore TUF trust-root client, Rekor v2 tiled logs, the `message_signature` arm, and embedded-SCT verification remain *Planned*, each re-openable behind a caller opt-in.

## Alternative encodings

- **C509 CBOR certificates** — *Parsing and encoding shipped (both certificate types, type-3 DER round-trip both directions).* `pki.schema.c509.parse` decodes a C509 certificate (draft-ietf-cose-cbor-encoded-cert) in both forms, natively signed and the CBOR re-encoding of a DER X.509 v3 certificate, over the strict deterministic-CBOR `pki.cbor` codec (RFC 8949 §4.2). A type-3 certificate is inverted back to the original DER byte for byte — decompressing the EC point, re-emitting each field as canonical DER, re-wrapping the ECDSA signature — so the original signature still verifies and the result round-trips through `pki.schema.x509.parse`; a field outside the reconstruction's covered set fails closed. `pki.schema.c509.encode` is the producing inverse: a DER X.509 v3 certificate forward-transforms to a compact type-3 C509 — compressing the EC point to its sign-of-y marker, a MAC-address commonName to a tag-48 EUI, a lone keyUsage to its integer shortcut, and re-expressing the ECDSA signature as a fixed-width r‖s — and self-verifies that the transform reproduces the source DER byte for byte; a `parse` result re-emits its native array. It decodes and encodes CBOR rather than DER, so it is an explicit-call surface rather than auto-routed by `pki.schema.parse`. Underpinning it, `pki.cbor.build` is a deterministic-CBOR encoder, the byte-exact inverse of the strict decoder. The compact per-extension value forms ship (draft-20 §3.3). The scalar extensions — `subjectKeyIdentifier`, `keyUsage`, `basicConstraints`, `extendedKeyUsage`, `inhibitAnyPolicy`, OCSP No Check, TLS Feature — and the general-name-bearing extensions — `subjectAltName`, `issuerAltName`, `nameConstraints`, `cRLDistributionPoints`, `freshestCRL`, `authorityInfoAccess`, `subjectInfoAccess`, and the full `authorityKeyIdentifier` in its keyId or keyId/issuer/serial form — encode and decode their specific compact CBOR value, in both directions and byte-exact, so a certificate interoperates with a conformant C509 encoder rather than only round-tripping through this decoder. A single shared `GeneralNames` value codec (§8.13) drives every general-name form: rfc822Name, dNSName, directoryName, URI, iPAddress including the RFC 9549 §2.2 address-plus-prefix-length name-constraints form, registeredID, and otherName with the hardware-module-name, SMTP-UTF-8-mailbox, and MAC-address specials. A registered extension without a value codec, a general name outside the §8.13 registry (an X.400 address, an EDI party name), or a value outside the covered set uses the unwrapped-OID byte-string form, and the round-trip is guarded so a non-canonical DER value can never encode lossily. `certificatePolicies` also ships (§8.9/§8.10): each policy identifier encodes as its registry integer (the CA/Browser Forum validation levels, the RFC 3779 RPKI resource-certificate policies, and the GSMA SGP.22 id-rspRole roles) or an unwrapped OID, and its CPS-URI and UserNotice-explicit-text qualifiers ride the compact form, while a UserNotice with a noticeRef, a non-UTF8String explicit text, or a qualifier outside the §8.10 registry falls back to the byte-string form. `policyMappings` and `policyConstraints` ship (§3.3): a policy mapping's issuer and subject domain policies each ride the same §8.9 registry-integer-or-OID policy space as `certificatePolicies`, and a policy constraints value rides the fixed `[requireExplicitPolicy, inhibitPolicyMapping]` skip-count pair, each field a non-negative integer bounded as the DER decoder bounds it or absent as CBOR null, both inverting to the DER extnValue byte for byte. `subjectDirectoryAttributes` also ships (§3.3/§8.6): each identification attribute rides its §8.6 registry integer, with the sign selecting the directory-string type, alongside its string values, or an unwrapped OID with raw value bytes for an attribute type outside the registry. It carries the multi-value `SET OF` form, since an attribute may hold more than one value, which distinguishes it from the single-value Name codec, and a per-attribute OID keeps the extension compact rather than dropping the whole value to the byte-string form. The RFC 3779 resource-delegation extensions ride their compact value form: `IPAddrBlocks` (int 32) and `ASIdentifiers` (int 33), plus their RFC 8360 v2 twins (34, 35), which the draft encodes identically. An address family carries its AFI and optional SAFI with either the delta-coded integer form or, once any address exceeds eight octets, the byte-string form; the choice is a SHALL, so decoding rejects the wrong one rather than admitting two encodings of one certificate. Addresses reach 2^64, so the delta chain and its bounds are computed without narrowing. A shape the compact form cannot carry exactly — a present `rdi`, an address list not in the RFC 3779 §2.2.3.6 canonical order, an AS number past 2^32-1 — falls back to the byte-string form with its bytes intact, so a non-conforming certificate is preserved and left visible to a validator rather than silently rewritten into a conforming one. Verified against the draft Appendix A.5 worked vector in both directions. Registered against draft-20 §8.6/§8.8/§8.9/§8.10/§8.11/§8.12/§8.13.

## Assurance and interoperability

- **Certificate linting** — *Shipped (RFC 5280 profile plus a representative CABF TLS BR subset), with the `pki inspect / lint / convert / verify` CLI; the full CABF corpus, S/MIME BR, and CRL and OCSP profiles are Targeted.* `pki.lint.certificate(pem | der | parsed, opts)` is a profile-conformance lint engine over the strict codec and schema: a declarative rule set that emits graded advisory findings, each with a stable id, a severity (fatal > error > warn > notice), a source, a spec-clause citation, and a message. Unlike the rest of the toolkit its advisory result surface never throws on the data path, since hostile bytes become a `fatal` `lint/unparseable` finding carrying the strict parser's code; only config-time misuse raises a typed `LintError`. `rules(profile)` and `profiles()` enumerate the registry. v1 covers the RFC 5280 certificate profile (serial sign and length, validity ordering, keyCertSign coherence, extension criticality — basicConstraints, nameConstraints, policyConstraints, and inhibitAnyPolicy must be critical and keyUsage should be — nameConstraints CA-scope, unknown critical extensions, empty-subject SAN, and SKI and AKI advisories including the end-entity subjectKeyIdentifier) and a representative CABF TLS BR subset (SAN required, CN-in-SAN, dNSName syntax, serverAuth EKU, weak keys, and the SC081v3 reducing validity ceiling of 398 to 200 to 100 to 47 days, gated to issuance date). Because this toolkit parses strict-DER, several profile violations a lenient linter reports specifically are rejected at parse and surface as one `lint/unparseable`. Pre-issuance linting is expected CA practice, and this covers it in JavaScript without a native dependency.
- **Interoperability gates** — *Shipped (OpenSSL and NSS); broader PKCS#12 matrix Targeted.* Cross-tool round-trip and parse checks against OpenSSL and NSS run as containerized release-acceptance gates; the Windows CAPI and macOS Keychain PKCS#12 cross-checks land with PKCS#12 building.
- **Fuzzing** — *Shipped.* A coverage-guided fuzz corpus against the ASN.1 codec and every parse path runs continuously, per-PR and nightly across a per-target matrix, each harness holding the contract that hostile bytes may only parse or throw a typed `PkiError`.
- **Independent security review** — *Planned.* A published security assessment of the parser and every crypto path as a release deliverable.

## Documentation

- **Source-generated reference and runnable examples** — *Shipped; example coverage expanding.* API documentation is generated from per-namespace `@module` and per-primitive `@primitive` source comment blocks and validated in continuous integration on the shipped runtime, so it cannot drift from the code. Example coverage keeps growing toward the common tasks — signing with your own CA, parsing a certificate, building a CSR with a SAN, PEM conversion — that otherwise generate repeated questions.

|---|---|---|
